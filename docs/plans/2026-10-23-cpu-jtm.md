# CPU JTM Implementation Plan

**Goal:** Use spare CPU capacity on the existing mining server for a named JTM worker and publish its public pool status in the existing dashboard.

**Architecture:** Keep the GPU workload intact. Run a restricted, low-priority `jtm-computer` systemd service, initially using a subset of physical cores. Create a dedicated wallet with the official Jetsam 1.5.1 node, back up its encrypted key and recovery material privately, and expose only its public receiving address. GitHub Actions continues to collect public APIs and publishes an additional independent JTM section.

**Tech Stack:** Ubuntu systemd, Jetsam 1.5.1 wallet, pool-adapted TowerWalk miner, Python standard library, existing HTML/CSS/JavaScript dashboard.

## Selection and current evidence

- Server: dual Xeon 8360Y, 72 physical cores / 144 logical CPUs, about 488 GiB available memory and initial load 0.36.
- JTM uses TowerWalk CPU PoW; official source: https://github.com/jetsam-chain/towerminer .
- Gozero JTM endpoint responds ready/synced; pool fee 1%, minimum 0.1 JTM, 9 confirmations, payment attempts every 60 seconds. https://pool.gozero.trade/JTM and https://jtm.pool.gozero.trade/api/stats .
- BNT uses Argon2id with 2 GiB per thread. Gozero currently advertises its BNT pool pause; do not use it for a new deployment. https://blocknetcrypto.com/ .
- Twitter/X keyword searches did not provide a verified current setup; use project release checksums and live pool APIs as operational evidence.
- Compared: JTM pool (selected: low RAM cost and public worker API); BNT pool (viable but memory intensive, needs another pool); JTM solo (requires ongoing local prover/node maintenance).

## Tasks

1. Verify release hashes before executing node or miner; inspect launcher and bundled documentation.
2. Create wallet under a separate service account with encrypted storage and private backups; never log or publish recovery secrets.
3. Smoke-test pool submission and worker naming; install a hardened service with CPU/memory caps and low priority only after accepted shares.
4. Add JTM API parser with strict units and public-field allowlist, stale-data fallback and tests for invalid schema, offline workers and secret/IP removal.
5. Add a responsive JTM section using the existing calm Chinese dashboard style. Do not include unknown JTM market prices or pool payouts in verified chain wallet valuation.
6. Run preflight, unit tests, live collection, desktop/mobile visual checks. Push focused changes to main and verify GitHub Pages deployment and public snapshot.

## Acceptance

`jtm-computer` submits accepted shares; original GPU service remains running; public monitor shows its CPU rate, online state, payout balance and update time; wallet backups exist privately on server and local machine.
